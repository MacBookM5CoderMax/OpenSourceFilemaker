# External SQL sources

A shadow table is a table in a hosted solution whose rows come from a SQL database. Tabularius keeps a SQLite mirror of those rows so layouts, finds, sorts, relationships, portals and calculations can read them through ordinary table occurrences.

## What works in this core

PostgreSQL connections support asynchronous design metadata, background mirror reads and the Execute SQL script step. MySQL, SQL Server and Oracle Connections binding is coming. The SQLite driver remains a local test stand-in and is never selectable in Connections. PostgreSQL is tested against scripted endpoints and Tabularius's own protocol server, but is unverified against a real server. <!-- known-difference: External SQL sources ;; PostgreSQL Connections behavior is unverified against a real server and other database Connections are not yet available ;; Some outside databases cannot be connected and real PostgreSQL behavior may differ ;; A run against real PostgreSQL, MySQL, SQL Server and Oracle servers -->

## Connect a PostgreSQL database

1. Open the admin console's **Connections** page and add **PostgreSQL**. Name it after the ODBC DSN, ignoring case, or set the data source's `connection` field to that name.
2. Enter `host`, `port` (default `5432`), `database` and `schema` (default `public`). List each hosted file allowed to use it in **Files**. For SQL connections, an empty list allows no files; existing storage, REST and email connections retain their existing default scope.
3. Choose `sslmode`: `verify-full` (default) verifies the certificate and hostname; `verify-ca` verifies the certificate; `require` encrypts without verifying the server; `disable` uses no TLS and is accepted only for `localhost`, `127.0.0.1` or `::1`. The optional `ca` field takes public PEM certificates, never a private key. Metadata and link-local destinations are refused at save time and again when connecting.
4. Enter `username` and `password` in their secret boxes. They are sealed on the server, never included in API replies or logs. With `require` or `disable`, cleartext and MD5 password requests are refused unless the administrator explicitly sets `allowPlaintextPassword` to `yes`. That option risks exposing the password to an unverified server; prefer verified TLS. The test result warns when TLS does not verify the server. <!-- known-difference-ok: unverified in this paragraph describes TLS configuration, not compatibility evidence -->
5. Press **Test**, which runs `SELECT 1` and shows at most 50 table names, then **Approve**. AI drafts remain unusable until a person approves them. Disabled connections and files outside the allowlist get no binding. Held and capture-only files cannot use SQL connections.
6. Create the ODBC data source, then create its shadow table in a separate design request. Metadata is fetched asynchronously before the design is applied.

For Execute SQL, an account needs full access or the `fmess` extended privilege. A script marked to run with full access does not grant `fmess` to its caller. The existing script network switch, call-stack file scope, capture-only rule and outbound test-mode host allowlist still apply. SQL text and result rows are never recorded in outbound logs. Results are discarded. Errors use the ESS code and a safe SQLSTATE diagnostic in `Get ( LastErrorDetail )`, rather than a raw database message that might contain a password or row.

The repository's script-text forms are `Execute SQL [ Data Source: "Sales" ; SQL: "SELECT 1" ]` and `Execute SQL [ Data Source: "Sales" ; Calculation: "SELECT " & 1 ]`. Native ODBC source and literal-text parameter decoding is unverified; converted steps without a decoded binding keep error 3 and explain how to bind a source. The ExecuteSQL calculation function remains separate. <!-- known-difference: External SQL sources ;; Execute SQL native source and literal-text parameter decoding and fmess behavior are unverified against FileMaker ;; Converted steps may need their data source and SQL specified again and some accounts are refused ;; A generated native script parameter comparison and execution against FileMaker ESS -->

Create an ODBC data source with a path such as `odbc:Sales`. A connection name matches the DSN without regard to case; the data source can name a different connection in its `connection` field. The host's resolver must enforce the connection's file scope. `createShadowTable` takes `dataSource`, `table`, optional `schema` and `name`, and optional `keys`. It reads the source columns and primary key, then creates the shadow table and a normal layout. When the SQL table has no primary key, give the names of columns that together are unique in `keys`. `syncShadowTable` adds new columns and marks missing columns as dropped. Neither operation changes the source table.

Mapped SQL types become Tabularius field types as follows:

| SQL type begins with | Field type |
|---|---|
| integer, int, smallint, bigint, numeric, real, decimal, float, double | number |
| char, varchar, text, or any other type not listed here | text |
| date | date |
| time | time |
| timestamp, datetime | timestamp |
| bytea, blob, binary, varbinary | container |

Fields added to a shadow table without a SQL column are supplemental fields. They stay local and are never sent to the SQL database. A mapped field cannot be renamed: the field name still identifies its outside column. Type mapping and supplemental-field behavior relative to FileMaker's ESS are unverified. <!-- known-difference: External SQL sources ;; SQL column type mapping and supplemental-field behavior relative to FileMaker ESS are unverified ;; A source value or supplemental field may be interpreted differently ;; A comparison with the same schema and values in a FileMaker ESS solution -->

## Refresh and limits

Before a record get, find, related read or portal read, Tabularius checks the mirror age. For PostgreSQL, an old mirror starts a background refresh and the read returns the current mirror immediately. A never-loaded mirror starts its first refresh and reports “The SQL data has not been loaded yet; try again in a moment”. The main thread never waits on network I/O. The design table status includes `sqlStatus.ageSeconds` and the last refresh error. `TABULARIUS_ESS_REFRESH_SECONDS` defaults to 5; set it to 0 to refresh on every read. A refresh reads the whole outside table. `TABULARIUS_ESS_MAX_ROWS` defaults to 100000; a larger table fails the background refresh without changing the mirror. Raise the cap only when the full table fits your host. Pushed-down finds are planned for a later item. A failed network refresh keeps the previous mirror and records the failure in its status. Retries double their delay from one second up to five minutes, with only one refresh in flight per table. The SQLite stand-in still refreshes synchronously and reports failures directly. Existing keys keep their record ids. After a deleted key has been removed by a refresh, inserting it again receives a new record id.

`TABULARIUS_ESS_TIMEOUT_SECONDS` defaults to 30 and bounds each bridge call. The synchronous test stand-in (SQLite) waits on the thread that serves requests, so a stand-in connection that did not answer in time is not asked again for a while: for a minute or twice the timeout, whichever is longer, doubling each time it still does not answer, up to 15 minutes, and back to normal after one answer; reads in that time fail at once with `8310` and say when it is asked again. `TABULARIUS_ESS_POOL` defaults to 4 and caps connections per name; network calls open a connection in a dedicated worker and close it when the call finishes; at most 64 network calls run across all names. The FileMaker error number for an ESS failure is unverified; this core consistently uses `8310`. Refresh timing, whole-table limits and that error number are Tabularius behavior, with FileMaker parity unverified. <!-- known-difference: External SQL sources ;; Refresh timing, whole-table row limit, record-id reuse and ESS error number are unverified against FileMaker ;; An ESS read may refresh or fail differently and report another error number ;; A comparison of refresh, row-cap and failure cases in FileMaker -->

## Writes

Network-backed record writes are currently refused with “Changing records of this SQL table is not available over a network connection yet”. Execute SQL can change the outside database; the mirror sees those changes on its next refresh. This limitation is explicit. <!-- known-difference: External SQL sources ;; Network-backed shadow record writes are unavailable ;; Record create, edit and delete return an ESS error while Execute SQL can change the outside database ;; Implement and verify asynchronous record writes against real servers -->

For the SQLite stand-in, create, edit and delete write mapped fields to the outside table and then commit the local mirror. Generated SQL keys are read back and mapped to stable local record ids. Supplemental fields stay in the mirror. File field validation and auto-enter run before the outside write. File serial numbers on a shadow table are local values; parity with FileMaker is unverified. The outside database supplies defaults for columns omitted by the file. <!-- known-difference: External SQL sources ;; File serial-number behavior on shadow tables is unverified against FileMaker ;; An auto-entered number may differ from a FileMaker ESS solution ;; A comparison of serial auto-enter and SQL defaults in FileMaker -->

An edit checks every mapped column against the values read into the mirror, using each database's NULL-safe comparison. If the outside row changed, the edit fails with error `306` and Tabularius refreshes the mirror row so the person can retry. A database constraint, permission or type failure returns the ESS error `8310`; the mirror write rolls back. The audit and record history use the ordinary write entries, including their surface and SQL connection name. If the outside row was already deleted, deleting its mirror row succeeds; FileMaker parity is unverified. <!-- known-difference: External SQL sources ;; Deleting a shadow row already gone from SQL succeeds here; FileMaker parity is unverified ;; A delete may report a different result in FileMaker ;; A comparison of already-deleted SQL rows in FileMaker ESS -->

One record or portal commit sends all its shadow-table changes for the same connection in one outside database transaction. Open Transaction defers shadow writes until Commit Transaction, one outside transaction per connection; Revert Transaction discards them. Across two connections there is no two-phase commit: the transactions are committed one after another, so a commit that touches two connections is not atomic: if the second connection's batch fails, the first connection keeps the rows it already wrote. A local mirror commit can also fail after an outside commit. These cross-database atomicity limits are part of this implementation. <!-- known-difference: External SQL sources ;; Shadow writes across connections, or between an outside database and the mirror, have no atomic commit ;; A later failure can leave one database committed and the other uncommitted ;; A recovery and transaction comparison against FileMaker ESS -->

Some changes to a shadow table are refused with the SQL source error (8310) because they would put the local copy and the outside table out of step: putting a file into a container field that is mapped to a BLOB column, reverting or undoing a delete (the audit revert, the data cleanup undo) and the point-in-time restore of a record. Delete again or create the record anew instead. <!-- known-difference: External SQL sources ;; Container uploads into a mapped BLOB column, undoing a delete and restoring a record as of an earlier time are refused on a shadow table ;; Those actions fail with the SQL source error instead of changing the record ;; A comparison with the same actions on an ESS table in FileMaker -->

The SQLite stand-in has automated write tests. The PostgreSQL, MySQL, SQL Server and Oracle write SQL has not been verified against real servers; PostgreSQL boolean, date and timestamp comparisons are tested over the local protocol endpoint; MySQL requests matched-row counts to avoid false conflicts on unchanged updates. `Truncate Table` on a shadow table remains unavailable. <!-- known-difference: External SQL sources ;; Truncate Table on a shadow table remains unavailable ;; A truncate that another ESS host permits fails here ;; A comparison of Truncate Table on a shadow table in FileMaker -->
